# 06 - Testing Strategy

Principle: anything with logic can run in a test without Next, without network and without global state. Tests prove the acceptance criteria of each issue and the isolation between tenants.

## 1. Pyramid

| Level | Scope | Tooling | Volume per issue |
|---|---|---|---|
| Unit | `domain/` rules and value objects (`Money`, `Quantity`, `Period`, average cost, profit formulas) | Vitest | Many, milliseconds each |
| Integration | One test file per use case against a real Postgres with migrations and RLS applied | Vitest + PGlite | One happy path, each failure path, one tenant isolation case |
| Component | Web components and pages with mocked API | Vitest + Testing Library + MSW | Key interactions only |
| End to end | Milestone deliverable through the real API and web | Playwright | One scenario per milestone, tagged `@Mn` |

## 2. API integration harness (PGlite)

- `createTestDb()` starts an in-memory PGlite instance, applies every migration from `apps/api/drizzle`, creates role `app_user` and returns a Drizzle client plus a `withTransaction` bound to it.
- Tests run as `app_user` with `set_config('app.tenant_id')` so RLS is active exactly as in production.
- One database per test file; tables truncated between tests. No Docker required on Windows.
- A generic `assertTenantIsolation(repositoryFactory)` helper seeds two tenants and asserts that reads, updates and deletes through the repository never cross. Every repository calls it.
- The Nest DI container is not booted for use case tests. Use cases are plain functions or classes receiving ports; tests build them with real repositories on the test DB and fake ports where IO would leave the process (email, storage).

## 3. Builders and seeds

- `test/builders/` per module: `aTenant()`, `anOwner()`, `aProduct().withPresentation(...)`, `aPurchase().withLine(...)`, `aSale()`. Builders produce valid defaults and allow overrides.
- `seedTenant(db, preset)` creates a tenant with preset catalogs and returns a `TenantContext` for owner and employee.
- No global fixtures. Each test states what it needs.

## 4. Web tests

- MSW handlers are generated from `@mini-market/contracts` schemas with example data, so a mock that drifts from the contract fails to compile.
- Component tests cover: role-aware rendering (employee never sees cost), form validation errors, money formatting, optimistic updates on the sale screen.
- No snapshot tests of whole pages.

## 5. Contract parity

- `@mini-market/contracts` is the single source of request and response shapes. API controllers parse input with it and type output with it. Web hooks type everything with it.
- A contract test per endpoint in the API asserts the real response validates against the response schema.
- OpenAPI generated by Nest is for documentation and external tooling, not the source of truth.

## 6. Time and randomness

- `Clock` from `@mini-market/shared-kernel` is injected. Tests use `FixedClock('2026-10-15T14:00:00Z')` to test month boundaries in `America/La_Paz`.
- Ids are generated through an injectable `IdGenerator`; tests may use a sequential one for readable assertions.

## 7. Playwright

- Lives in `e2e/`. Runs against API and web started by Turborepo (`pnpm e2e` builds, starts and runs).
- Uses a dedicated Postgres (PGlite server mode or a local Postgres in CI) seeded through the provisioning script, not Supabase.
- Supabase Auth is replaced in e2e by a test JWT issuer configured via env (`AUTH_TEST_MODE=true`), so e2e does not depend on an external service.
- One spec file per milestone, tagged `@M0` to `@M8`. Each spec exercises the milestone deliverable end to end: for M4, sell, check stock decreased, open receipt, void, check stock restored.

## 8. Coverage gates (CI)

| Path | Lines and branches |
|---|---|
| `apps/api/src/modules/*/domain` | 80% |
| `apps/api/src/modules/*/application` | 80% |
| `packages/shared-kernel` | 100% |
| `presentation/`, `apps/web` | no gate; covered by e2e and component tests |

## 9. Traceability

- Every acceptance criterion in an issue has an id `AC-n`. The test that proves it carries the comment `// AC-n` on the `it(...)` line.
- `/verify-issue` greps for `AC-n` markers and reports criteria without a test. A criterion may instead point to a manual check recorded in the issue's Verification section when automation is not possible (print layout, for example).

## 10. Closing a milestone

1. Every issue in the milestone is Done and merged to `main`.
2. `pnpm e2e --grep @Mn` passes on `main`.
3. The epic issue's manual checklist (API and web) is executed on the dev deployment and ticked.
4. `docs/03-roadmap.md` status updated; milestone closed in GitHub.
